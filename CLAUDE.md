# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

An IronFlock (Record Evolution) edge-device app that packages the upstream [wg-easy](https://github.com/wg-easy/wg-easy) WireGuard VPN server. There is no VPN application source code here — only integration glue: a Dockerfile extending the pinned upstream image, an entrypoint script, a Python companion process (four modules), the AI assistant's knowledge docs, and IronFlock platform manifests in `.ironflock/`. The app is deployed to Linux edge devices (amd64/arm64) through the IronFlock platform, which injects runtime environment variables (`DEVICE_KEY`, `DEVICE_NAME`, `ENV`, `TUNNEL_DOMAIN`, `WG_PORT`, user parameters from `env-template.yml`) and runs the container privileged.

## Commands

- Build: `docker build -t wireguard-easy .` (not possible in this dev container; verify on a device)
- Templates: `python3 <ironflock-templates skill>/scripts/validate.py .` (the `ironflock-templates` skill of IronFlock's Claude Code plugin). Must report 0 errors.
- Knowledge docs + ai-template: `python3 check_knowledge.py` (needs `pyyaml` and `knowledge_core`, found as pip package or as the sibling checkout `../knowledge_core`).
- Syntax: `python3 -m py_compile *.py`, `bash -n entrypoint.sh`.
- There are no tests. The companion's state logic can be smoke-tested offline against a SQLite DB built from wg-easy's migrations with `vpn_state.wg_dump` etc. monkeypatched. Final verification means deploying via IronFlock and reading the container logs — `entrypoint.sh` prints a startup banner ("wg-easy startup config") and the companion logs with the `[ironflock]` prefix.

## Architecture

`Dockerfile` extends `ghcr.io/wg-easy/wg-easy:<WG_EASY_VERSION>` (the version is pinned once in the `ARG` and exported as `WG_EASY_VERSION`), adds Python 3, `ironflock` and `ironflock-knowledge-core` (pinned in `requirements.txt`; git is installed only for the pip step), the four Python modules, `entrypoint.sh` and `knowledge/` under `/ironflock`. The CMD is replaced with `entrypoint.sh`, which orchestrates startup and then `exec`s the unmodified upstream server (`node /app/server/index.mjs`).

`entrypoint.sh` is plain bash (deliberately: all Python logic lives in the modules) and runs, in order:

1. Enables forwarding sysctls (`ip_forward`, `src_valid_mark`) — required once apps move to bridge networking; no-op under today's host networking.
2. Symlinks `/etc/wireguard -> /data`. wg-easy stores everything in a SQLite DB at `/etc/wireguard/wg-easy.db`, but only `/data` is a persistent volume on IronFlock devices. (`/data` also holds the agent-maintained `env/` directory, so it is never truly empty.)
3. Exports wg-easy v15 unattended-setup vars (`INIT_ENABLED`, `INIT_HOST` from `TUNNEL_DOMAIN`, `INIT_PORT=51820`), defaults `DISABLE_VERSION_CHECK=true`, and prints the startup banner (password masked). `INIT_PORT` must never be seeded from `WG_PORT`: wg-easy's first-boot setup writes it into the wg ListenPort too (see invariants).
4. Runs a foreground Python self-test (imports `ironflock`, `knowledge_core`, `yaml` with a 20 s timeout) and prints it as `PYTHON CHECK` in the banner, then launches `register_device.py` in a background restart loop (stderr merged into stdout, each attempt logged as `[ironflock] launching companion (attempt N)`, so an unreachable router can never block the VPN and a crash never goes unnoticed) and `exec`s the unmodified upstream server.

The companion process (`register_device.py`, lifetime of the container) owns all platform integration:

- `endpoint_sync.py` — **loop 1, deliberately WAMP-independent** (every 10 s): computes the public VPN endpoint via `getRemoteAccessUrlForPort(51820, protocol="udp", remote_port_environment="WG_PORT")` and rewrites `host`/`port` in wg-easy's `user_configs_table` when it changed; enforces `interfaces_table.port = 51820`; re-applies `INIT_ALLOWED_IPS` to `user_configs_table.default_allowed_ips` when the parameter differs from the last-applied value (state file `/data/.ironflock_applied_allowed_ips`). Required because the device agent activates/deactivates tunnels and rewrites `/data/env/*.txt` in RUNNING containers without a restart, while wg-easy reads `INIT_*` only on first boot. Returns events (dicts) instead of logging so the caller can record them.
- `vpn_state.py` — read-only collection of the gateway's state: wg-easy's SQLite (read-only), `wg show <iface> dump`, sysctl, iptables NAT rule, local Web UI port. `collect(endpoint)` returns one snapshot with the ordered **setup checklist** (`checks`, results OK/INFO/WARNING/PROBLEM with hints), the merged client list (status CONNECTED/OFFLINE/NEVER_CONNECTED/DISABLED/EXPIRED; connected = handshake ≤ 180 s), and the derived gateway status (OK/WARNING/PROBLEM/SETUP_PENDING/STARTING). `route_check()` is the pure computation behind the AI route tool. Never raises: unreadable sources become check results.
- `register_device.py` — **loop 2** (every 30 s, after the connection is up, triggered early by sync events): publishes the snapshot on change to the tables `gateways` (entity per `device_key`), `clients` (per `device_key, client_id`; removed clients get `deleted: true`), `checks` (per `device_key, check_id`; vanished checks are closed with OK/"cleared"), `traffic` (per minute, only clients whose counters moved, kB/s rates) and `events` (append-only queue, flushed each tick). Writes use `append_to_table` and catch `RuntimeError` (platform unreachable beyond the reconnect window) to retry next tick; `last published` state is only updated after a successful write. `web_url` is published in development runs and production installs alike: development runs get their own HTTPS and UDP tunnels, so the dev board embeds the run's Web UI and the endpoint sync works there too. The HTTPS label of a development run carries a `-dev` suffix (`4749-wireguard_easy-51821-dev.app.ironflock.com`), which the SDKs (ironflock-py 1.11.0, ironflock-js 1.10.0) do not add yet; `endpoint_sync.get_web_ui_url()` appends it to the SDK's URL when `ENV` is not `PROD`, and is a no-op once the SDK returns a `-dev` label. Use that helper, never `getRemoteAccessUrlForPort(51821)` directly. The first state row waits up to 90 s for wg-easy (Web UI answering, wg interface up), so a restart does not publish a transient PROBLEM.
- `ai_tools.py` — the AI assistant's device functions (`vpn.status`, `vpn.clients`, `vpn.diagnose`, `vpn.route_check`, `vpn.resync_endpoint`), tolerant of every WAMP calling convention and never raising, plus registration of the knowledge library (`knowledge/**/*.md`, served as `app_knowledge.list`/`app_knowledge.get` by `ironflock-knowledge-core`). `main()` (the SDK's `mainFunc`) registers them and then runs loop 2 forever: **it must never return**, because the SDK closes the connection when it does.

`knowledge/` holds the guides the assistant serves on demand (frontmatter: `id`, `title`, `kind` ∈ {guide, reference}, `summary` ≤ 250 chars, `topic`, `keywords`, `aliases`, `verified`). They describe this app's actual behavior; when behavior changes, update the matching doc (`reference.architecture`, `reference.checks_and_tables`, `reference.parameters` are the ones most tied to code).

## Critical invariants

- **First-boot-only semantics:** every `INIT_*` variable is applied by wg-easy only while the DB is empty (`initialSetup` bails on `setup.done`, i.e. `general_table.setup_step == 0`). Afterwards settings live in the DB and are changed in the Web UI — with two app-managed exceptions in `endpoint_sync.py`: the client-facing Host/Port (overwritten whenever the tunnel endpoint changes; do not edit in the Admin UI — clobbered within ~10s) and the default Allowed IPs (re-applied when the `INIT_ALLOWED_IPS` parameter changes; Web UI edits persist otherwise). `INIT_DNS`, `INIT_IPV4_CIDR`/`INIT_IPV6_CIDR` (must be set together) and the initial credentials remain strictly first-boot-only.
- **wg-easy DB facts (verified against the v15.5.0 source):** every config download / QR request re-reads `user_configs_table` (single row, id = interface name, `wg0`) from SQLite, so external UPDATEs take effect immediately without restarting the server. wg-easy's own connection runs with `busy_timeout=0` (its 0001 migration also requests WAL), so external writers must keep transactions to one short UPDATE and must not write while first-boot setup runs (both sync functions gate on `setup_step == 0`); `vpn_state.read_db` opens the DB with `mode=ro`. `interfaces_table.port` is the wg ListenPort and must stay 51820 (the tunnel forwards the public port there) — wg-easy's first-boot `updateHostPort` writes `INIT_PORT` into BOTH `user_configs_table.port` and `interfaces_table.port`, which is why `INIT_PORT` stays 51820 and the sync loop repairs a wrong ListenPort back to 51820 (effective on the next container restart). Columns used: `general_table.setup_step`; `interfaces_table.name/device/port/ipv4_cidr/ipv6_cidr/mtu`; `user_configs_table.host/port/default_allowed_ips/default_dns/default_mtu/default_persistent_keepalive` (list columns are JSON string arrays); `clients_table.id/name/enabled/ipv4_address/ipv6_address/allowed_ips/expires_at/public_key/persistent_keepalive`. Private keys are never read.
- **Two distinct network paths:** the Web UI (port 51821) travels over an HTTPS tunnel subdomain; the VPN itself is UDP and cannot — clients need `Endpoint = <tunnel domain>:<public UDP port>`. Both URLs must be composed by the ironflock SDK's `getRemoteAccessUrlForPort` (never hardcode hosts or reimplement the routing; the one exception is the `-dev` label suffix described under `register_device.py` above): it combines the device identity, `TUNNEL_DOMAIN`, and the tunnel-assigned public UDP port `WG_PORT` (declared via `remote_port_environment` in `port-template.yml`; on appliance/instance devices `WG_PORT_CLOUD` on `CLOUD_TUNNEL_DOMAIN` wins), reading live values from the agent-maintained files in `/data/env` with start-time env vars as fallback. The public UDP port is forwarded to 51820 inside the container.
- **The companion must ignore SIGHUP** (`trap '' HUP` before the background loop in `entrypoint.sh`). The entrypoint is PID 1 (exec-form `CMD`), so when it `exec`s dumb-init, dumb-init's TTY detach (TIOCNOTTY) makes the kernel SIGHUP the whole foreground process group, background companion included. On IronFlock devices containers run with a TTY, and without the trap the companion dies right after `launching companion` with no further output.
- **Persistence depends on the symlink:** the DB must physically live at `/data/wg-easy.db`. The banner warns if `/etc/wireguard` is not linked to `/data`; the `db_persisted` check reports it on the board.
- **wg-easy validation:** admin username min 2 chars, password min 12 chars — shorter values make first login fail silently (the gateway then shows `SETUP_PENDING`).
- **Tables are the contract:** every key the companion writes must be a column in `data-template.yml` (the platform drops unknown keys silently). `GATEWAY_COLUMNS`/`CLIENT_COLUMNS` in `register_device.py`, the check dict in `vpn_state.collect`, the traffic and event rows, and the five tables must stay in step; the board binds to these column ids and the ai-template's `data_access` reads their descriptions.
- **Device functions ↔ ai-template:** `ai_tools.TOPICS` and knowledge_core's `DEFAULT_TOPICS` must match the `topic:` values in `.ironflock/ai-template.yml`; `check_knowledge.py` enforces it. Handlers must return JSON-serializable dicts and never raise.
- **Duplicated docs:** the app description exists twice — `README.md` and the `guide-md` markdown widget inside `.ironflock/board-template.yml` (sections "Three places", "First login", "Options", "split tunnel", "When something does not work", "Requirements"). Update both together, including the option tables, and keep `env-template.yml` descriptions and `knowledge/reference/parameters.md` consistent with them.
- **Version bumps:** the upstream version is pinned only in the Dockerfile `ARG WG_EASY_VERSION`, but v15-specific behavior (unattended setup, INIT_* names, DB columns above, no 32-bit ARM, `WG_INTERFACE`) is referenced in `entrypoint.sh` comments, `vpn_state.py`, `README.md`, `env-template.yml` and the knowledge docs. When bumping, diff the upstream `src/server/database/migrations` and `repositories/*/schema.ts` against the columns listed above, and check the unattended-setup docs.
- The literal port numbers passed to `getRemoteAccessUrlForPort` — `WEB_UI_PORT = 51821` and `VPN_PORT = 51820` in `vpn_state.py` — must match the declarations in `port-template.yml`.
- `requirements.txt` must pin `ironflock` ≥ 1.10.0: 1.5.3 added the `protocol`/`remote_port_environment` parameters and live `/data/env` reads the endpoint sync depends on; 1.10.0 added the automatic restore of registered device functions after a reconnect, which the AI tools rely on. `ironflock-knowledge-core` is installed from its Git tag (no PyPI package).
- **Board routing:** gateway pages route by `device_key` (`/gateways/<device_key>/...`); widgets on them filter with `{column: device_key, useRoute: true, value: '2'}`. Entity reads use the `latest: true` filter; there is no `latest_flag` column. The board editor rewrites `board-template.yml` on save (sorts widgets, pins versions); change the file in place rather than regenerating it from scratch once users have edited it.
