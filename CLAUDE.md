# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

An IronFlock (Record Evolution) edge-device app that packages the upstream [wg-easy](https://github.com/wg-easy/wg-easy) WireGuard VPN server. There is no VPN application source code here — only integration glue: a Dockerfile extending the pinned upstream image, an entrypoint script, a Python companion process (four modules), the design documents in `design/`, the AI assistant's knowledge docs, and IronFlock platform manifests in `.ironflock/`. The app is deployed to Linux edge devices (amd64/arm64) through the IronFlock platform, which injects runtime environment variables (`DEVICE_KEY`, `DEVICE_NAME`, `ENV`, `TUNNEL_DOMAIN`, `WG_PORT`, user parameters from `env-template.yml`) and runs the container privileged.

## Commands

- Build: `docker build -t wireguard-easy .` (not possible in this dev container; verify on a device)
- Templates: `python3 <ironflock-templates skill>/scripts/validate.py .` (the `ironflock-templates` skill of IronFlock's Claude Code plugin). Must report 0 errors.
- Knowledge docs + ai-template: `python3 check_knowledge.py` (needs `pyyaml` and `knowledge_core`, found as pip package or as the sibling checkout `../knowledge_core`).
- Syntax: `python3 -m py_compile *.py`, `bash -n entrypoint.sh`.
- There are no tests. The companion's state logic can be smoke-tested offline against a SQLite DB built from wg-easy's migrations with `vpn_state.wg_dump` etc. monkeypatched. Final verification means deploying via IronFlock and reading the container logs — `entrypoint.sh` prints a startup banner ("wg-easy startup config") and the companion logs with the `[ironflock]` prefix.

## Architecture

The design lives in `design/` (read it before changing the app, and update it in the same change): `design/architecture.md` (parts, tables and their one writer, data flows, parameters, ports, device functions, failure behaviour), `design/entities.md` (entities and keys), `design/board.md` (brief, route tree, pages, colours) and `design/decisions.md` (dated decisions). The short version:

`Dockerfile` extends `ghcr.io/wg-easy/wg-easy:<WG_EASY_VERSION>` (the version is pinned once in the `ARG` and exported as `WG_EASY_VERSION`), adds Python 3, `ironflock` and `ironflock-knowledge-core` (pinned in `requirements.txt`; git is installed only for the pip step), the four Python modules, `entrypoint.sh` and `knowledge/` under `/ironflock`. `entrypoint.sh` (plain bash on purpose) enables the forwarding sysctls, symlinks `/etc/wireguard -> /data`, exports the wg-easy v15 unattended-setup vars (`INIT_ENABLED`, `INIT_HOST` from `TUNNEL_DOMAIN`, `INIT_PORT=51820`, never `WG_PORT`; see invariants), defaults `DISABLE_VERSION_CHECK=true`, prints the startup banner with a foreground `PYTHON CHECK`, starts `register_device.py` in a background restart loop (`[ironflock] launching companion (attempt N)`) and `exec`s the unmodified upstream server.

The companion process (`register_device.py`, lifetime of the container) owns all platform integration:

- `endpoint_sync.py`: **loop 1, deliberately WAMP-independent** (every 10 s): `sync_endpoint_once` writes the public VPN endpoint from `getRemoteAccessUrlForPort(51820, protocol="udp", remote_port_environment="WG_PORT")` into `user_configs_table.host/port` when it changed and enforces `interfaces_table.port = 51820`; `apply_default_allowed_ips` writes a board-saved default into `user_configs_table.default_allowed_ips` (after `parse_allowed_ips` validated it). `get_web_ui_url` is a thin wrapper of `getRemoteAccessUrlForPort(51821)`: ironflock 1.11.2 returns a development run's own `-dev` tunnel URL itself. Functions return events (dicts) instead of logging so the caller can record them.
- `vpn_state.py`: read-only collection of the gateway's state: wg-easy's SQLite (read-only), `wg show <iface> dump`, sysctl, iptables NAT rule, local Web UI port. `collect(endpoint)` returns one snapshot with the ordered **setup checklist** (`checks`, OK/INFO/WARNING/PROBLEM with hints), the merged client list (CONNECTED/OFFLINE/NEVER_CONNECTED/DISABLED/EXPIRED; connected = handshake ≤ 180 s) and the gateway status (OK/WARNING/PROBLEM/SETUP_PENDING/STARTING). `route_check()` is the pure computation behind the AI route tool. Never raises.
- `register_device.py`: at start, after the connection is up, writes the **registration row** to `gateways` (`device_id` = `DEVICE_KEY`, `device_name`, `web_url`, `deleted: false`), then follows the board: subscribes to `gateway_settings` and `gateways` first, then reads the newest `gateway_settings` row for its `device_id`. A settings row is applied (by loop 1, once wg-easy's setup is done) only when its `tsp` is newer than the one in `/data/.ironflock_settings_tsp`, so a restart never re-applies an old row over a later Web UI edit; an invalid value is reported with `report_error` and a `settings_rejected` event and not retried. A `gateways` row with `deleted: true` (only the board writes that) refreshes `fleet_summary`. **Loop 2** (every 30 s, woken early by sync events) writes **partial rows** (key, `tsp`, changed columns; the platform carries the rest over) to `gateways`, `clients` (key `client_key` = `<device_id>-<client_id>`; the first row of a client in a run writes `deleted: false`, a client removed in wg-easy gets `deleted: true`/`REMOVED`), `checks` (key `device_id` + `check_id`; vanished checks are closed with OK/"cleared"), `traffic` (per minute, only clients whose counters moved) and `events` (queue flushed each tick), and refreshes `fleet_summary` after a `gateways` write. Writes catch `RuntimeError` and retry next tick; what was written is remembered only after success. The first state row waits up to 90 s for wg-easy.
- `ai_tools.py`: the AI assistant's device functions (`vpn.status`, `vpn.clients`, `vpn.diagnose`, `vpn.route_check`, `vpn.resync_endpoint`), tolerant of every WAMP calling convention and never raising, plus registration of the knowledge library (`knowledge/**/*.md`, served as `app_knowledge.list`/`app_knowledge.get` by `ironflock-knowledge-core`). `main()` (the SDK's `mainFunc`) registers them, registers the gateway, follows the board and then runs loop 2 forever: **it must never return**, because the SDK closes the connection when it does.

`knowledge/` holds the guides the assistant serves on demand (frontmatter: `id`, `title`, `kind` ∈ {guide, reference}, `summary` ≤ 250 chars, `topic`, `keywords`, `aliases`, `verified`). They describe this app's actual behavior; when behavior changes, update the matching doc (`reference.architecture`, `reference.checks_and_tables`, `reference.parameters` are the ones most tied to code).

## Critical invariants

- **First-boot-only semantics:** every `INIT_*` variable is applied by wg-easy only while the DB is empty (`initialSetup` bails on `setup.done`, i.e. `general_table.setup_step == 0`). Afterwards settings live in the DB and are changed in the Web UI, with two app-managed exceptions: the client-facing Host/Port (overwritten by `endpoint_sync.py` whenever the tunnel endpoint changes; do not edit in the Admin UI, clobbered within ~10 s) and the default Allowed IPs, which users set per gateway on the board (`gateway_settings`) and the companion applies (last writer wins against a Web UI edit). `INIT_ALLOWED_IPS` only seeds that default on the first boot; the app no longer re-applies the parameter. `INIT_DNS`, `INIT_IPV4_CIDR`/`INIT_IPV6_CIDR` (must be set together) and the initial credentials remain strictly first-boot-only.
- **wg-easy DB facts (verified against the v15.5.0 source):** every config download / QR request re-reads `user_configs_table` (single row, id = interface name, `wg0`) from SQLite, so external UPDATEs take effect immediately without restarting the server. wg-easy's own connection runs with `busy_timeout=0` (its 0001 migration also requests WAL), so external writers must keep transactions to one short UPDATE and must not write while first-boot setup runs (both sync functions gate on `setup_step == 0`); `vpn_state.read_db` opens the DB with `mode=ro`. `interfaces_table.port` is the wg ListenPort and must stay 51820 (the tunnel forwards the public port there) — wg-easy's first-boot `updateHostPort` writes `INIT_PORT` into BOTH `user_configs_table.port` and `interfaces_table.port`, which is why `INIT_PORT` stays 51820 and the sync loop repairs a wrong ListenPort back to 51820 (effective on the next container restart). Columns used: `general_table.setup_step`; `interfaces_table.name/device/port/ipv4_cidr/ipv6_cidr/mtu`; `user_configs_table.host/port/default_allowed_ips/default_dns/default_mtu/default_persistent_keepalive` (list columns are JSON string arrays); `clients_table.id/name/enabled/ipv4_address/ipv6_address/allowed_ips/expires_at/public_key/persistent_keepalive`. Private keys are never read.
- **Two distinct network paths:** the Web UI (port 51821) travels over an HTTPS tunnel subdomain; the VPN itself is UDP and cannot — clients need `Endpoint = <tunnel domain>:<public UDP port>`. Both URLs must be composed by the ironflock SDK's `getRemoteAccessUrlForPort` (never hardcode hosts or reimplement the routing): it combines the device identity, `TUNNEL_DOMAIN`, and the tunnel-assigned public UDP port `WG_PORT` (declared via `remote_port_environment` in `port-template.yml`; on appliance/instance devices `WG_PORT_CLOUD` on `CLOUD_TUNNEL_DOMAIN` wins), reading live values from the agent-maintained files in `/data/env` with start-time env vars as fallback. The public UDP port is forwarded to 51820 inside the container.
- **The companion must ignore SIGHUP** (`trap '' HUP` before the background loop in `entrypoint.sh`). The entrypoint is PID 1 (exec-form `CMD`), so when it `exec`s dumb-init, dumb-init's TTY detach (TIOCNOTTY) makes the kernel SIGHUP the whole foreground process group, background companion included. On IronFlock devices containers run with a TTY, and without the trap the companion dies right after `launching companion` with no further output.
- **Persistence depends on the symlink:** the DB must physically live at `/data/wg-easy.db`. The banner warns if `/etc/wireguard` is not linked to `/data`; the `db_persisted` check reports it on the board.
- **wg-easy validation:** admin username min 2 chars, password min 12 chars — shorter values make first login fail silently (the gateway then shows `SETUP_PENDING`).
- **Tables are the contract:** every key the companion writes must be a column in `data-template.yml` (the platform drops unknown keys silently). `GATEWAY_COLUMNS`/`CLIENT_COLUMNS` in `register_device.py`, the registration rows, the check dict in `vpn_state.collect`, the traffic and event rows, and the six tables must stay in step; the board binds to these column ids and the ai-template's `data_access` reads their descriptions. Entity tables are keyed by columns the gateway writes (`device_id`, `client_key`), never `device_key`, which a board-written delete row cannot set; `device_name` is a plain column in `gateways` and `clients` for the same reason. Nothing removes a gateway automatically: only the board's "Remove gateway" writes `deleted: true`.
- **Device functions ↔ ai-template:** `ai_tools.TOPICS` and knowledge_core's `DEFAULT_TOPICS` must match the `topic:` values in `.ironflock/ai-template.yml`; `check_knowledge.py` enforces it. Handlers must return JSON-serializable dicts and never raise.
- **Duplicated docs:** the app description exists twice: `README.md` and the `guide-md` markdown widget inside `.ironflock/board-template.yml` (sections "Three places", "First login", "Options", "split tunnel", "When something does not work", "Requirements"). Update both together, including the option tables and where the default Allowed IPs is set (the gateway's Settings page), and keep `env-template.yml` descriptions and `knowledge/reference/parameters.md` consistent with them.
- **Version bumps:** the upstream version is pinned only in the Dockerfile `ARG WG_EASY_VERSION`, but v15-specific behavior (unattended setup, INIT_* names, DB columns above, no 32-bit ARM, `WG_INTERFACE`) is referenced in `entrypoint.sh` comments, `vpn_state.py`, `README.md`, `env-template.yml` and the knowledge docs. When bumping, diff the upstream `src/server/database/migrations` and `repositories/*/schema.ts` against the columns listed above, and check the unattended-setup docs.
- The literal port numbers passed to `getRemoteAccessUrlForPort` — `WEB_UI_PORT = 51821` and `VPN_PORT = 51820` in `vpn_state.py` — must match the declarations in `port-template.yml`.
- `requirements.txt` must pin `ironflock` ≥ 1.11.2: 1.5.3 added the `protocol`/`remote_port_environment` parameters and live `/data/env` reads the endpoint sync depends on; 1.10.0 the automatic restore of registered device functions and the subscription catch-up after a reconnect; 1.11.0 `refresh_transform`; 1.11.2 returns a development run's own `-dev` tunnel URL from `getRemoteAccessUrlForPort`. `ironflock-knowledge-core` is installed from its Git tag (no PyPI package).
- **Board routing:** gateway pages route by `device_id` (`/gateway/<device_id>/...`, tabs clients, traffic, checks, events, settings); widgets on them filter with `{column: device_id, useRoute: true, value: '2', dataType: numeric}`. Client pages route by `client_key` (`/client/<client_key>`, `useRoute` on `client_key`, string). Entity reads use the `latest: true` filter plus the OR filter on `deleted` (gateways, clients); there is no `latest_flag` column. The board editor rewrites `board-template.yml` on save (sorts widgets, pins versions); change the file in place rather than regenerating it from scratch once users have edited it.
